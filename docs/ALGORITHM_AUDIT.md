# 算法与数据核查（2026-10-22）

## 核查结论

本次能确认程序中的缺陷和数据来源关系，尚不能确认整套推演符合某部古籍，也没有进行预测准确率验证。对照采用虚构样例，不涉及真实个人资料。

## 一、为什么同一小时不变

源码 `main.py` 先查十四表得到本命数、十二辟卦、本命条文和 108 岁流年，最后才调用 `calculate_keke()`。`known_shengxiao` 在最后修改 `k_true` 和部分扩展字段，不回写前面的本命与流年计算。

对虚构样例「男，1984-08-15，求测 2025-04-20 10:00」逐分钟计算 12:00～12:59：

| 观察项 | 基线结果 |
| --- | --- |
| 本命数 | 60 次均为 349 |
| 兄弟条文号 | 60 次均为 7789 |
| 八刻初定值 | 5、6、7、8 随 15 分钟段改变 |
| 108 岁校正条文号序列 | 只有一种 |

机器记录见 [minute-baseline.json](audit/minute-baseline.json)，标明测试的源提交。这说明“分钟已经改变了一些元数据，但主要查表结果不依赖分钟”，不能据此推定每分钟都应该更换一条断语。重新接入主结果需要先选定可核验的流派、书版与公式，不能随意加分钟偏移。

## 二、考刻实现的明确缺陷

基线 `keke_module.kao_ke()` 仅使用输入中的第一个六亲。无匹配时仍返回第 1 刻，并把第 1 个候选的 `match` 改为 `True`。这是程序状态错误；不能当成已知事实验证成功。

该函数还以 `(基数 + 刻序) % 10` 推生肖，实际只能生成前十个地支，无法生成戌、亥对应的狗、猪。它构造的条文号即使存在，也不等于断语正文确实在说目标亲属和生肖。尚未找到可逐页核验的底本来支持这套公式，因此保留为待校的旧版规则，不把 `%10` 直接改成 `%12` 后声称恢复古法。

## 六、迭代方向

- 修复虚假匹配状态；所有已提供的六亲必须参与，候选和冲突逐项展示。
- 分开“钟表时间初定刻”和“旧规则六亲候选”，无匹配不强指定。
- 用完整两小时八刻检查时间敏感性，额外诊断每分钟变化；不捏造分钟公式。

## 考刻修复进展

无匹配强行标真、只用首个六亲的问题已修复。所有已填六亲参与候选交集，狗/猪明确未支持；存在冲突或未支持条件时不输出锁定刻。此修复没有补造古籍公式，也没有让考刻候选改写十四表本命与流年。


## 时间校验修复进展

网页 23 点原先先换成次日 0 点再取八刻，误把子时的前半段定位到后半段。现分别保留钟表坐标与 V2 历法换日输入，23:05 为第 1 刻、次日 00:05 为第 5 刻。新增两小时八刻/逐分钟对照，直接报告输出种数。对 1984-08-15 男、求测 2025-04-20 10:00 的午时逐分钟 120 次实测，本命数仍为 349、本命及流年序列各只有一组；这是被测规则的结构，不把新界面说成预测准确率提升。

还有未证公式：`calculate_target_number()` 的旧秘数取模范围为 1～12000，而本库条文号范围是 1001～13000，前 1000 个数没有对应条文。需要底本明确编号体系后才可决定平移或换算，不用偏移凑出可命中的文字。


## 表格缺项与静默回退修复

`DB/14-9.csv` 的第 1240、1270 行都为“正刻,670,遁”，正刻 700 缺项。数据加载后 1500 行只有 1499 个唯一键。旧查表在专用键缺失时借用通用映射，通用映射先收录初刻，可能把正刻缺项伪装成已匹配。现在查不到精确刻别/本命数就标记 `MISSING_HEXAGRAM_ENTRY`，不借其他刻别生成本命条文。原 CSV 未改；重复与缺项由离线审计显式输出，`table_quality_ok=false`。已知缺陷固定在审计基线中，新增或变化的缺陷会使完整性审计失败。修复原表必须提供可核对书页或上游确认。


## 自动代码审查后的边界修复

当可评估条件已互相冲突时，状态优先返回 `no_match`，即使另有狗/猪条件尚不支持；避免把已确定的数值冲突误说成仅因规则未支持而无法判断。回归测试保留全部条件和空的支持条件候选集，仍不把该数值判断升级为事实验证。
